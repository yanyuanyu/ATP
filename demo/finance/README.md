# 金密杯金融协作演示与测试

作品为面向数字金融多智能体协作的国密身份认证与安全通信系统。金融演示使用用户、商户、支付三个管理域，完成订单发起、三条签名报价事件、用户授权、模拟支付、业务回执和账本核对。商旅住宿是示例商品，金额单位为人民币分。

## 启动

需要 Python 3.11+、已启动的 Docker Desktop Linux 引擎。前端已构建，基础金融演示不需要配置模型 Key。仓库根目录双击 `启动金融演示.cmd`，或 PowerShell 执行：

```powershell
.\启动金融演示.ps1
.\启动金融演示.ps1 -Action status
.\启动金融演示.ps1 -Action stop
```

浏览器地址为 http://127.0.0.1:18088/ 。停止保留订单、账本、身份密钥。首次构建需要可获取基础镜像和依赖的网络；已存在的本机 ATP 基础镜像可以复用。所有金融逻辑和协议代码均由当前仓库 `src` 覆盖构建，不依赖旧项目的源码目录。前端修改后在 `demo/docker/demo/web` 执行 `npm ci` 和 `npm run build`，再重新启动以更新镜像。

金融演示使用 `atp-jinmi` Compose 项目、`jinmi-*` 容器、172.32.0.0/24 至 172.32.3.0/24 网络，与原密码竞赛部署分开。若本机已有占用这些地址的其他部署，需先处理冲突，不能复用不明网络。用户、商户和支付 ATP 服务器分别只加入自己的域网络，跨域流量经原有 TLCP 网关。商户和支付业务智能体分别部署在商户域和支付域，控制器承载用户侧编排和证据展示。

## 演示步骤

主页面沿用原来的布局、聊天、拓扑、协议路径、数据包与四智能体执行视图。工具栏增加“金融订单与账本”入口，业务操作在同一套卡片样式的窗口内完成。

1. 点击原页面工具栏的“金融订单与账本”，创建订单，接收并验证三条商户 SM2 签名报价，默认两晚最低合计340元。
2. 核对报价，点击“确认订单并授权模拟支付”。未点击前不会执行付款。
3. 等待支付域回执；成功后展示订单编号、金额和回执编号，并自动查询账本。刷新按钮可再次通过 ATP 获取账本快照。
4. 点击金额不符、收款方不符、报价篡改、缺少授权，检查真实拒绝回执；点击重复付款幂等，检查原回执被复用且余额不再次变化。
5. 展开金融窗口内的“金融业务关联记录”，核对发送方、接收方、nonce、关联订单和结构化结果，导出 JSON。
6. 关闭金融窗口，在原页面查看同一次金融操作触发的真实抓包、协议路径和包头详情。

金融业务智能体使用确定性工具执行，以便稳定复现安全和账本测试，不调用模型生成金额、签名或记账结果。原有真实 LLM 四智能体聊天和执行视图直接保留在主页，`/protocol` 是同一页面的兼容入口。模型协作需要在 `demo/docker/.env` 配置模型接口后重启。原有模型业务为酒店查询、价格订阅和模拟付款，不能将其模型结果与金融验收混写成同一轮运行。

## 实现与信任边界

- `src/atp/finance/ledger.py`：商户签名报价、整数分计价、币种与收款方校验、授权标志、报价有效期、单笔限额、测试余额、事务记账和订单幂等。报价由独立业务 SM2 密钥签名，支付端预置信任对应公钥；商户私钥仅挂载到商户智能体。
- `worker.py`：业务智能体和持久化回复队列。回复提交失败后继续发送；业务账本按订单去重，消息层按 nonce 区分。
- `hub.py` / `api.py`：用户编排、报价验证、回执与发送方/任务/请求 nonce 关联、持久化证据及本机 API。accepted 仅表示本域接收，PAID 需要支付回执。
- 原 ATP 核心提供域身份认证、SM2/SM3签名、SM4载荷保护与TLCP域间传输。接收域服务器会解密消息，不声称服务器无法读取业务内容。
- 模拟账本仅在这一套测试余额和数据库内保证同一订单一次记账；不承诺外部银行系统的端到端一致性。
- 用户端先将订单状态、待发业务请求持久化，再发送到ATP。每次发送前保存请求nonce关联，即使HTTP响应丢失，后续业务回执仍可关联。未完成操作按5秒递增、最长60秒间隔重试，业务订单及付款内容保持不变，每次使用新传输nonce以遵守ATP防重放规则；账本按订单和请求指纹防止重复记账。有效业务回执结束重试，已完成操作忽略迟到回执。
- 金融收件端将整批消息和取信游标在同一SQLite事务内保存，业务处理成功后才标记已处理。暂时处理失败或进程重启后从本地收件箱继续处理。该机制用于金融Mailbox，不改变通用ATPClient的默认取信语义。HTTP认证错误及服务端错误会抛出异常，不再当成空收件箱。
- 新部署分别生成用户、商户和支付角色口令。检测到旧版`runtime/mailbox-password`时会兼容旧账户并提示仍使用共享口令，不会静默更改服务端账户密码或清空数据卷。既有部署的凭据隔离需要同步迁移服务端账户和客户端口令，不能只删除旧口令文件。
- 自动恢复仅覆盖新版持久化的请求。旧版因HTTP响应丢失而未留下请求内容或nonce的历史操作，无法从现存数据自动重建。持久化收件箱、请求尝试和业务记录目前没有自动清理，应按部署规模安排保留策略。
- 演示控制器和原协议页面带有本地管理权限，只发布到127.0.0.1，不能直接作为互联网生产支付服务。

## 测试与报告材料

第五章完整材料通过以下脚本生成，输出到仓库旁的“第五章测试材料”目录：

- `chapter5_model.py`：真实四智能体完整协作及订单参数核对。
- `chapter5_collect.py`：全量与分类回归、网络隔离、三种消息模式、64 KiB队列、确认丢失去重、三轮整组重启、金融端到端与浏览器验收。
- `chapter5_figures.py`：根据原始数据生成莫兰迪学术图表、SVG与CSV，使用matplotlib和numpy。
- `chapter5_screenshots.py`：通过Python Playwright和本机Edge截取真实界面局部。
- `chapter5_assemble.py`：生成测试矩阵、图像总览、来源校验和完整ZIP。
- `chapter5_review.py`：检查300 dpi图像、总览导航和手机布局；总览预览服务使用本机18090端口。

```powershell
.\启动金融演示.ps1 -Action test
```

`acceptance.py --outage` 会仅停止、恢复 `jinmi-server-payment`，并重启 `jinmi-finance-payment`。测试产生新的虚构订单和测试账本记录，不调用收费模型。运行前应停止人工操作，避免并行测试干扰余额差值判断。

`evidence/` 保留当前验收 JSON、JUnit、桌面/手机截图以及测试汇总。协议性能使用含订单编号、付款方、收款方、金额和币种的JSON消息，附加填充后为精确1 KiB或64 KiB。加解密耗时不包含消息签名、网络传输、排队、取信及业务记账。100 ms、2 s、30 s属于作品自定验证目标，不是金密杯统一评分阈值。

`runtime/` 保存本机生成的商户密钥、测试口令、TLS/TLCP证书和Compose配置；它被Git忽略，不能纳入公开源码材料。金融账本保存在Docker命名卷。不要使用 `down -v` 清除需要保留的状态。

故障恢复回归：`python -m pytest tests/test_finance_recovery.py`。这些测试通过模拟HTTP和临时数据库验证提交响应丢失、记账后的重试、收件持久化失败、部分处理后重启以及HTTP错误传播；不代替Docker端到端验收。仓库`evidence/`中的既有结果不会随源码修改自动更新，重新部署后应再执行端到端验收。
